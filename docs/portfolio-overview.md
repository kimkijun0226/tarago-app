# TaraGo 프로젝트 소개

> 반복해서 도착정보를 확인하는 번거로움을 줄이는, 위치·시간 기반 버스·지하철 알림 앱

TaraGo는 주변 버스 정류소와 지하철역을 지도에서 검색하고, 도착정보를 확인하거나 원하는 조건에 맞춰 알림을 받을 수 있는 모바일 서비스다. 사용자가 지정한 요일·시간대 또는 정류소·역 주변 진입 여부를 기준으로 알림을 제공하는 데 초점을 두었다.

현재 iOS 앱을 TestFlight로 테스트하고 있으며, 약 3명의 테스터에게 피드백을 받아 화면 구성과 사용 흐름을 개선하고 있다. React Native 기반으로 iOS와 Android를 함께 대상으로 개발하지만, 두 플랫폼의 공개 스토어 출시를 의미하지는 않는다.

## 1. 해결하려는 문제

대중교통을 이용할 때 정류소·역을 검색하고 도착정보를 반복해서 확인해야 하는 불편함이 있다. 자주 이용하는 시간대와 장소가 정해져 있어도 매번 같은 조회를 해야 한다.

TaraGo는 사용자가 필요한 조건을 미리 설정해 두고, 해당 조건에 맞는 도착정보를 알림으로 받도록 구성했다. 단순 정보 조회뿐 아니라 사용자의 시간과 위치를 알림의 실행 조건으로 연결했다.

## 2. 주요 기능

### 지도 기반 교통 탐색

- NAVER Map SDK로 현재 위치 주변의 버스 정류소와 지하철역을 표시한다.
- 버스 정류소·지하철역·일반 장소를 검색하고 최근 검색 기록을 제공한다.
- 정류소별 버스 도착정보와 노선·경유 정류소를 확인한다.
- 지하철의 호선·방면별 도착정보와 시간표를 확인한다.

### 예약 알림

- 반복 요일과 시작·종료 시간을 설정한다.
- 대상 정류소·버스 노선 또는 지하철역·호선·방면을 지정한다.
- 도착 전 알림 단계를 설정해 서버가 조건을 감시하도록 한다.
- 알림 활성화·수정·삭제와 알림 대상 화면으로 이동하는 흐름을 제공한다.

### 위치 알림

- 정류소·역의 지정 반경에 들어오면 첫 번째·두 번째 차량의 도착정보를 안내한다.
- 반경 안에 있는 동안 선택한 간격으로 다시 알리고, 이탈 상태가 서버에 반영되면 반복 조회·알림을 중단한다.
- 앱의 위치 감지와 서버의 조회·발송 작업을 분리했다. 실제 감지 시점은 위치 권한, GPS 정확도, OS 백그라운드 정책과 네트워크 상태의 영향을 받는다.

### 알림 내역과 사용자 의견

- 발송한 알림 내역을 별도 화면에서 확인한다.
- 제목, 선택적인 내용·이미지를 포함한 의견을 보낼 수 있다.
- 서버에서 입력과 첨부파일을 검증한 후 Gmail SMTP로 전달한다.

## 3. 시스템 구성

```text
모바일 앱: React Native / Expo
  ├─ Expo Router: 화면과 탭·스택 이동
  ├─ NAVER Map SDK: 지도 표시
  ├─ TanStack Query: 서버 데이터 조회·캐시·갱신
  ├─ Zustand / React state: 공유 UI 상태와 화면별 편집 상태
  └─ Location / TaskManager / Notifications: 위치 감지와 알림 수신
                   │ HTTPS REST API
                   ▼
NestJS API 서버
  ├─ Bus: 정류소·도착정보·노선과 지역별 공급자 연결
  ├─ Subway: 실시간 도착정보·역 정보·시간표
  ├─ Alerts: 기기 인증·알림 설정·발송 내역
  ├─ Worker: 실행 조건 확인·도착정보 조회·푸시 발송
  ├─ Mobility: 장소 검색
  └─ Feedback: 사용자 의견 메일 발송
       │                        │
       ▼                        ▼
PostgreSQL / PostGIS       외부 데이터·서비스
정류소·출처·알림·발송 기록    TAGO / 서울 / 경기 / TMAP / Expo Push
```

앱과 서버를 별도 저장소로 관리한다. 앱은 외부 기관의 비밀 API 키를 직접 소유하지 않고, 서버가 외부 응답을 앱에서 사용하는 데이터 형식으로 정규화한다.

| 화면 이동 | Expo Router | 파일 기반 라우팅과 탭·스택 구성 |

| 제스처·시트 | Gorhom Bottom Sheet, Gesture Handler, Reanimated | 지도 위 시트와 터치·애니메이션 처리 |

| 백엔드 | Node.js, NestJS, TypeScript | 기능별 모듈과 API·비즈니스 로직 구성 |

저장소의 현재 주요 버전은 Expo 57, React Native 0.86, React 19, NestJS 12, TypeScript 6이다. 버전은 문서 작성 시점의 package.json 기준이다.

## 5. 코드 구성 원칙

### 모바일: 화면 조립과 기능 구현 분리

```text
src/
├─ app/             라우트와 화면 조립
├─ features/
│  ├─ map/          지도 선택·카메라·오버레이
│  ├─ bus-stop/     정류소·버스·노선 조회
│  ├─ subway/       지하철 조회와 알림
│  ├─ bus-alert/    알림 설정·런타임·발송 내역
│  ├─ mobility/     검색
│  └─ feedback/     의견 보내기
└─ shared/          공통 API·UI·테마·타입·공유 상태
```

기능별로 API 요청, 모델·훅, UI를 분리했다. 서버 응답은 TanStack Query를 원본으로 사용하고, Zustand는 지도 선택이나 탭 표시 같은 공유 UI 상태에 사용한다. 한 화면에서만 필요한 값은 React state에 둔다.

SQLite에 보관하는 알림 사본은 백그라운드 위치 작업을 위한 저장 데이터다. 화면의 서버 상태와 별개의 원본으로 취급하지 않는다.

### 서버: 기능 모듈과 공급자 분리

Bus, Subway, Alerts, Mobility, Feedback 모듈로 책임을 구분했다. 버스 데이터는 서울·경기·TAGO 공급자를 분리하고, 지역과 원본 식별자에 맞춰 조회한 결과를 공통 형식으로 합친다. DB 접근은 PostgreSQL 연결 풀을 사용하는 계층에서 처리한다.

## 6. 기술적으로 강조할 구현

### 서로 다른 교통 데이터의 식별자와 위치 통합

같은 정류소가 여러 공급자에서 다른 ID로 제공될 수 있다. 정류소와 공급자별 출처를 분리해 저장하고, 노선 조회 시 원본 공급자 정보와 경유 순번을 유지하도록 구성했다.

지도의 표시 좌표와 교통 API의 조회 식별자도 구분했다. 마커가 가리키는 위치를 바꾸면서 알림 대상이나 반대편 정류소까지 잘못 연결하지 않도록 다루는 것이 주요 과제였다.

### 지도 조회와 실시간 조회의 수명 분리

자주 변하지 않는 정류소 위치는 타일 단위로 조회하고 캐시를 재사용한다. 실시간 도착정보는 별도의 짧은 갱신 주기로 처리한다. 새로운 지도 영역을 불러오는 동안 이전 타일 결과를 유지해 표시가 갑자기 사라지는 상황을 줄이도록 했다.

서버에서도 동일 요청의 진행 중 Promise를 공유하고 캐시를 사용해 중복 외부 호출을 줄인다. 버스 도착정보는 성공 응답을 15초간 재사용하고, 갱신 실패 시 30초 이내의 최근 응답을 제한적으로 활용한다.

### 필요한 조건에서만 알림 조회 실행

서버 Worker가 활성 요일·시간 또는 유효한 위치 진입 상태를 확인한 뒤 도착정보를 조회한다. 앱의 알림 미리보기도 비활성화·시간 범위 밖·위치 반경 밖의 조건에서 조회를 제한한다.

이를 통해 지속적인 전체 조회 대신 사용자가 실제로 필요한 조건에 맞춰 외부 API 호출을 제어하도록 설계했다. 조회량 감소율이나 비용 절감률은 별도 측정값이 없어 수치로 기재하지 않는다.

### 시간·위치 이벤트와 중복 발송 처리

한국 시간과 자정을 넘는 예약 구간을 처리하고, 위치 진입·이탈에는 관측 시각을 사용한다. 발송 조건별 키와 DB 기록을 이용해 같은 조건에서의 중복 발송을 억제한다.

푸시 요청 성공과 사용자 기기의 실제 수신은 구분한다. 네트워크·OS 실행 정책·푸시 서비스의 영향을 받으므로 정확히 한 번의 수신이나 즉시 도착을 보장한다고 표현하지 않는다.

### 기기 인증과 비밀 정보 분리

앱의 기기 인증 정보는 SecureStore에 보관하고 서버는 자격 증명 해시로 기기를 확인한다. 저장된 알림과 내역은 해당 기기 인증을 거쳐 조회·변경한다. 외부 API 키와 SMTP 인증 정보는 서버 환경변수로 관리한다.

## 7. 배포와 피드백 기반 개선

서버 main 브랜치의 push를 GitHub Actions와 Windows self-hosted runner에 연결했다. 의존성 설치, 린트, 테스트, 빌드를 거쳐 실행 결과물을 릴리스 폴더로 배포하고, 응답 확인과 실패 시 이전 시작 설정을 복구하는 절차를 구성했다.

iOS는 Xcode Archive를 통해 TestFlight로 배포해 테스트하고 있다. 현재 약 3명의 테스터에게 피드백을 받고 있으며, 지도 검색, 마커 구분, 정보 위계, 시트와 설정 화면의 이동 흐름을 반복해서 개선하고 있다.

포트폴리오에는 다음과 같이 적을 수 있다.

> TestFlight를 통해 실제 기기에서 베타 테스트를 진행하고, 약 3명의 테스터에게 받은 피드백을 바탕으로 지도 검색과 알림 설정 흐름을 개선했습니다. 기능 구현 이후에도 사용자가 대상을 선택하고 설정을 완료하는 과정을 확인하며 UI와 내비게이션을 반복적으로 다듬었습니다.

## 8. 현재 개발 상태와 표현 범위

- 지하철의 개별 행선지 복수 선택, 실시간 정보가 없을 때의 시간표 보완 등은 현재 개발 소스에 포함되어 있다. 이번 확인 시 관련 앱·서버 변경은 미커밋 상태이므로 운영 배포 완료 기능과 구분한다.
- 시간표 기반 안내는 실시간 정보와 출처를 구분하며 실제 운행과 차이가 있을 수 있다.
- 도착 조건별 재알림 간격을 문장형 흐름으로 연결하는 새로운 예약 설정은 논의 단계이며 완료 기능에 포함하지 않는다.
- Cloudflare Workers·D1 이전은 저장소에 계획 문서가 있으나 현재 실행 코드의 기술 구성으로 기재하지 않는다.
- 이번 문서는 저장소 코드·설정과 사용자 제공 테스트 현황을 기준으로 작성했다. 부하 테스트, 사용자 전환율, 비용 절감률은 확인되지 않았다.
- 개발 기간, 참여 인원, 개인별 기여도는 별도 확인 후 추가한다.

## 9. 포트폴리오용 짧은 소개

TaraGo는 버스·지하철의 도착정보를 확인하고, 사용자가 지정한 시간대나 정류소·역 주변 진입 조건에 맞춰 알림을 받을 수 있는 모바일 서비스입니다. React Native·Expo로 앱을 개발하고, NestJS·PostgreSQL/PostGIS로 교통 데이터 조회와 알림 처리 서버를 구성했습니다. 서로 다른 공공 교통 API의 데이터를 공통 형식으로 통합하고, 타일 캐시·요청 공유·조건부 조회를 적용해 불필요한 호출을 줄이도록 설계했습니다. 현재 TestFlight에서 약 3명의 테스터에게 피드백을 받아 지도와 알림 설정 경험을 개선하고 있습니다.
