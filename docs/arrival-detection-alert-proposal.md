# 차량 확인 후 반복 알림 — 설계 제안

기존의 `도착 N분 전`과 별개로 `차량이 확인되면`을 선택한다. 예약은 지정한 요일·시간, 위치 알림은 확인된 위치 반경 안에서만 작동한다. 이 문서는 검토용 제안이며 서버와 저장 형식에는 아직 적용하지 않았다.

## 사용 흐름

- 도착 N분 전: 현재 단계별 알림을 유지한다.
- 차량이 확인되면: 기준 분을 묻지 않는다. 첫 유효 차량이 25분 뒤든 5분 뒤든 바로 알리고, 선택한 1·3·5·10분 간격으로 현재 첫 두 차량의 도착정보를 알린다.
- 이미 차량이 있는 상태에서 활성화해도 최초 알림을 한 번 보낸다.
- 차량이 정류소·역을 지난 뒤에는 다음 차량으로 이어간다. 차량이 없는 동안에는 반복 푸시를 보내지 않는다.
- 예약 종료, 위치 반경 이탈, 비활성화 시 해당 조건에 의한 조회·발송을 중단한다. 동일 대상에 별도의 활성 예약이 있으면 그 예약은 자체 조건을 따른다.

## 조회와 중복 방지

외부 API 조회 주기와 사용자에게 알리는 주기는 분리한다. 같은 정류소·역의 활성 대상들은 기존 서버 조회와 캐시를 공유한다. 정보가 없는 동안에는 낮은 빈도로 확인하고, 가까운 차량이 있으면 기존 실시간 조회 간격으로 확인한다. 활성 조건이 없으면 외부 API를 호출하지 않는다. 감시 자체에는 조회가 필요하므로 정보 없음 상태를 무조회로 만들지는 않는다.

차량 ID·열차 ID와 운행 회차, 유효 조건이 시작된 세션, 발송 간격을 조합해 중복을 막는다. 번호판 뒤 4자리만으로 차량을 식별하지 않는다. ID가 없는 공급자는 노선·방향·운행 시간 묶음으로 제한하고 반복 주기당 한 번만 발송한다. 수신 실패·오래된 캐시를 차량 없음이나 새 차량 출현으로 취급하지 않는다. 잠깐 누락됐다가 복구된 동일 차량에도 최초 알림을 다시 보내지 않는다.

## 실시간과 시간표

실시간에서 새로 확인된 차량과 시간표에 예정된 열차는 구분한다. 시간표가 항상 존재한다는 이유로 매번 새 출현으로 판단하지 않는다. 기존 지하철 시간표 보완을 사용할 때는 `시간표 기준`을 표시하고, 해당 운행 회차의 감시 시작을 세션에서 한 번만 처리한다. 실시간으로 전환되어도 같은 열차의 최초 알림을 다시 보내지 않는다.

## 적용 범위

버스·지하철 공통 `발송 조건`(도착 임박 / 차량 확인)과 `반복 간격`을 앱·서버에서 함께 검증한다. 기존 알림은 기본값을 도착 임박으로 유지한다. 조회 조건 판단은 기존 시간·방면·반경 규칙을 재사용하며, 폴링과 푸시 워커에 발송 조건만 추가한다.
