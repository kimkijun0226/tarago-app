# 피그마 기술 문서 작성 규칙

## 적용 범위
타라고 기술 문제를 설명하는 Figma 문서와 발표 자료에 적용한다.
기존 파일 https://www.figma.com/design/3N19uooJtbwrtuPFbvLBeb/Tarago 안에서 작성한다.
별도 앱·웹사이트·새 프레젠테이션 파일을 만들지 않는다.

## 문서 구조
문제 하나마다 ‘원인’과 ‘분석 및 해결’ 두 장을 만든다.
각 문제는 한 줄, 왼쪽은 원인, 오른쪽은 분석 및 해결 순서로 배치한다. 분석만 별도 장으로 반복하지 않는다.
새 문제는 다음 줄에 배치한다. 서로 다른 문제의 설명을 섞지 않는다.
기존 프레임을 수정하고, 사용자가 요청하지 않은 버전·페이지·보관본을 늘리지 않는다.

## 제목
단계와 대상 문제를 함께 적고 명사형으로 끝낸다.
- 원인 : 하행 정류장에서 회차 전 버스의 정보가 표시되지 않는 문제
- 분석 및 해결 : 회차 경로를 반영한 하행 도착시간 예측
‘공유한다’, ‘사용한다’, ‘했다’처럼 대상 문제가 드러나지 않는 제목은 피한다.
제목은 한 줄로 작성한다. 길면 핵심 문제와 대상이 남도록 문장을 줄이고 세부 조건은 본문으로 옮긴다. 한 줄에 맞추려고 글씨를 지나치게 작게 만들지 않는다.

## 설명 문체
상황 그림 아래에 설명을 배치한다. 그림 위에 본문을 쓰지 않는다.
기존 상태·원인은 짧은 명사형으로 작성한다. ‘조회했었습니다’, ‘처리했으며’처럼 과거형을 겹치거나 설명을 장황하게 늘리지 않는다.
예: ‘기존 방식 : 선택한 하행 정류장의 공식 응답만 조회’ / ‘확인된 불편 : 회차 전 차량 미포함 시 도착시간 표시 누락’.
분석·해결도 ‘분석 : 회차 전 차량과 하행 정류장의 연결 계산 누락’ / ‘해결방안 : 회차 전후 경유 순서를 반영한 예상 도착시간 계산’처럼 적는다.
현재 반영된 변경은 ‘로컬 소스 반영’, 제안은 ‘개선안·구현 전’, 미확인 결과는 ‘효과 미측정’으로 명시한다.
쉬운 한국어를 우선하고 ETA는 ‘예상 도착시간’, 캐시는 처음에 ‘응답 보관(캐시)’으로 설명한다.
노선 번호·정류장·차량의 움직임을 구체적으로 적는다.

## 그림과 도표 선택
모든 장을 같은 사각형 세 개와 화살표로 만들지 않는다.
- 원인: 실제 상황을 설명하는 그림 + 사용자에게 보이는 앱 상태 개념도.
- 분석: 입력·판단·처리·결과가 구분되는 워크플로우 또는 시간축·호출 수식.
- 해결방안: 개선 후 상황·이전/이후 비교·개선된 앱 상태를 보여준다.

## 회차 버스 그림
버스 아이콘과 노선 번호를 직접 배치하고 ‘회차점으로 이동 중인 52번 버스’처럼 설명한다.
차량 진행 방향과 회차점의 돌아가는 화살표를 표시한다.
선택한 하행 정류장은 차량·일반 정류장과 다른 색으로 표시하고 색뿐 아니라 이름·강조 테두리로도 구분한다.
정류장 응답에 도착정보가 없는 앱 상태를 함께 보여준다.
해결 후 그림은 같은 정류장과 차량을 유지해 무엇이 달라지는지 비교할 수 있어야 한다.
회차점으로 이동 중인 차량은 파랑, 선택한 하행 정류장을 이미 지나간 차량은 주황으로 구분하고 각 상태를 글로 표시한다. 두 차량은 같은 시각의 서로 다른 차량이며, 같은 차량을 복제한 것처럼 오해하게 만들지 않는다.
선택 정류장 표식과 이름은 같은 중심축에 맞춘다. 이름은 표식 바로 아래에서 가로 중앙 정렬한다.
‘회차 지점’ 문구는 회차 화살표 바로 옆에 배치한다. 회차점 이름을 경로와 떨어진 위치에 두지 않는다.
오른쪽 앱 정보가 어떤 정류장인지 정류장 표식에서 패널로 이어지는 연결선으로 표시한다. 패널 제목도 ‘선택한 하행 정류장’처럼 동일하게 적는다.
정보 연결선은 실제 도로·차량 진행 경로와 구분한다. 주황 점선과 ‘이 정류장의 도착정보’ 같은 레이블을 사용하고 교차·가림을 피한다.

## 워크플로우 도형
입력·시작은 원 또는 둥근 캡슐, 판단은 마름모, 처리는 사각형, 출력은 문서형/결과 패널로 구분한다.
조건선에는 있음/없음, 예/아니오를 적는다.
연결 방향과 합류를 검수한다. 색은 데이터 상태를 보조하며 의미는 글자로도 전달한다.
도형 내부 글자는 가로·세로 중앙에 맞추고 제목·설명 묶음 전체를 도형 안에 넣는다. 최소 안쪽 여백을 확보하고, 특히 마름모는 사각 경계가 아니라 실제 도형 내부에 글자가 들어가는지 확인한다.
도형 밖의 있음/없음 분기 레이블은 해당 연결선 가까이에 둔다. 패널·도형을 연결할 때 대상과 출처가 시각적으로 명확해야 한다.

## 상태와 정확도
앱 화면을 직접 캡처한 것이 아니면 ‘화면 개념도’라고 표시한다.
예상 도착 분·차량 번호·정류장명·요청 개수의 예시는 실측 데이터와 구분한다.
‘개선 후 예시’가 실제 구현 완료처럼 보이지 않도록 ‘설계 예시·구현 전’을 적는다.
확인된 코드·사용자 관찰·로컬 변경·미검증 제안을 섞지 않는다.
차량 ID 연속성·대기시간·다음 운행이 검증되지 않았으면 검증 전으로 표시한다.
총 호출량 절감이나 429 원인을 실제 계측 없이 확정하지 않는다.

## 시각 규칙
흰색·연회색·검정 중심에 파란 강조색을 유지한다.
차량/진행 경로는 파랑, 선택 정류장은 주황, 개선 결과는 녹색으로 구분한다.
한글 Noto Sans KR, 본문 26~28, 제목 38~43, 도표 레이블 20~25 기준.
원인·분석 및 해결의 2열 배치와 그림 아래 본문 위치를 일관되게 유지한다.
텍스트·도형은 편집 가능하게 만들고 그림·제목·본문·각주가 겹치지 않도록 확인한다.

## 문서 전체에 적용하는 상세 디자인 기준
아래 기준은 회차 그림 한 장에만 적용하지 않고 모든 문제의 원인·워크플로우·개선 그림에 공통으로 적용한다.
- 사용자가 직접 조정한 최신 Figma 프레임을 시각적 기준으로 삼는다. 수정한 문구·수치 예시·색상·배치를 먼저 읽고 보존한다.
- 제목 위의 ‘문제 1’ 같은 탐색 문구와 장식성 단계를 제거한다. 한 줄 제목을 그림 바로 위 약 20~28 간격에 두며, 기존보다 조금 큰 42 전후 크기를 사용한다.
- 그림·제목·본문의 좌우 기준선을 맞춘다. 큰 빈 공간이나 일정하지 않은 간격을 없앤다.
- 실제 설명 대상인 경로는 8~10 굵기, 보조 경로는 3~4 굵기로 차이를 준다. 두껍게 강조할 구간은 데이터의 의미와 일치해야 한다.
- 회차 경로·합류선·분기선은 직선과 부드러운 곡선을 조합한다. 불필요한 지그재그, 짧은 꺾임, 중복 선분, 비뚤어진 화살촉을 제거한다.
- 정류장과 정보 패널의 연결은 가능한 한 ‘짧은 세로선 + 긴 가로선 + 방향이 맞는 화살촉’으로 단순화한다. 레이블을 선 위에 겹쳐 놓지 않는다.
- 선의 끝점은 대상 도형의 경계에 정렬한다. 화살촉은 경로의 진행 방향과 일치시킨다. 같은 의미의 연결선은 같은 굵기·색·점선 간격을 사용한다.
- 도형 안 글자의 가로·세로 중앙 정렬, 일정한 내부 여백, 줄바꿈, 표식과 레이블의 중심축을 함께 검수한다.
- 모든 텍스트는 실제 글자에 맞는 가로·세로 자동 크기(WIDTH_AND_HEIGHT)를 기본으로 한다. 긴 빈 텍스트 영역을 남겨 정렬 기준을 왜곡하지 않는다. 명시적 줄바꿈으로 줄 길이를 제어한다.
- 도형 중앙에 놓을 때는 텍스트 박스를 실제 글자 크기로 맞춘 다음 (도형 크기 - 텍스트 크기) / 2로 위치를 계산한다. 제목·설명은 두 줄의 실제 높이와 간격을 합친 묶음으로 중앙 정렬한다.
- 버스 옆 진행 화살표는 버스 도형의 세로 중앙에 맞춘다. 차량·처리 도형·출력 패널을 잇는 선도 대상 도형의 중앙 포트에서 시작하거나 끝나도록 실제 좌표로 검수한다.
- ‘가운데 정렬’ 속성만 설정하고 빈 폭이 큰 텍스트 영역이나 잘못된 연결선 좌표를 그대로 두지 않는다. 범위·중심점 검수와 화면 검수를 모두 수행한다.
- 해결 그림에는 개선된 결과가 구체적으로 보여야 한다. 예를 들어 도착시간·남은 정류장 수를 같이 보여주되 ‘가정 예시·구현 전’을 명시한다.
- ‘분석 및 해결’ 본문은 왜 문제가 생겼는지와 무엇을 바꾸었거나 바꿀지를 구분해 짧게 작성한다. 기존 분석 내용을 단순 삭제해 근거를 잃지 않는다.
- 부분 수정 후에도 남은 모든 장에 같은 기준이 적용됐는지 확인한다. 한 장의 세부 수정만으로 전체 문서 개선을 완료했다고 보고하지 않는다.

## 재사용 프롬프트
다음 문제를 타라고 Figma 파일의 기술 설명 자료로 작성한다.
문제별로 원인·분석 및 해결 두 장을 왼쪽에서 오른쪽으로 배치한다.
제목은 ‘단계 : 대상과 문제를 명시한 명사형’으로 작성한다.
그림 아래에는 ‘기존 방식 / 확인된 불편 / 분석 / 해결방안’의 짧은 명사형으로 설명하고, 반영한 조치와 계획을 명확히 나눈다. ‘했었습니다’ 같은 장황한 과거형은 사용하지 않는다.
원인은 상황과 앱 상태 그림을 사용하고, 분석 및 해결은 판단 근거가 읽히는 워크플로우·시간축·개선 후 비교 그림 중 알맞은 형식을 사용한다.
회차 버스에는 노선 번호·진행 방향·회차 화살표·색으로 구분한 선택 정류장을 표시한다.
선택 정류장과 앱 정보 패널을 명시적인 연결선으로 묶고, 이미 그 정류장을 지나간 차량도 주황색과 방향 화살표로 설명한다.
정류장 이름은 표식 바로 아래 중앙, 회차점 이름은 회차 화살표 옆에 둔다. 도형 안 글자는 충분한 여백을 두고 가로·세로 중앙 정렬한다.
텍스트 컨테이너는 실제 글자 크기에 맞춘 뒤 정렬하고, 모든 버스 진행 화살표는 버스의 세로 중앙에 배치한다.
제목은 핵심 문제를 담아 한 줄로 작성한다.
‘문제 1’ 표시를 없애고 제목을 그림 바로 위에 조금 크게 둔다. 핵심 선과 보조 선의 굵기를 구분하고 모든 연결선을 간결하고 부드럽게 정리한다. 이 기준을 문서 전체에 적용한다.
앱 개념도와 가정 수치는 실제 화면·실측 자료와 구분한다.
기존 스타일을 유지하고 이 문서의 정확도·검수 기준을 따른다.
